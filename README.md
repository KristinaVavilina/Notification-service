# Разработка распределенного сервиса отправки уведомлений на разные источники
— сервис, отправляющий уведомления в реальном времени на различные источники, обеспечивая при этом высокую надежность доставки и поддержку нескольких типов сообщений (текстовые, мультимедийные и т.д.)

## 🧩 Архитектура решения
Схема отражает микросервисную архитектуру системы уведомлений, спроектированную для обеспечения масштабируемости, отказоустойчивости и легкости расширения.

### Notification Gateway
Единая точка входа (REST API). Принимает HTTP-запросы от клиентов, валидирует их и передает в шину сообщений.
### Infrastructure Abstraction Layers (Libs)
Для унификации кода и упрощения поддержки выделены общие библиотеки:
- **MessageQueueConnectionLib** — абстракция над брокерами сообщений (RabbitMQ / Kafka).
- **DBConnectionLib** — слой работы с данными (PostgreSQL / MongoDB).
- **MonitoringConnectionLib** — единый клиент для сбора метрик.
### Каналы отправки (Services)
Независимые микросервисы (Email, SMS, Push), работающие как консьюмеры (consumers). Каждый сервис слушает свою очередь, что позволяет масштабировать их независимо друг от друга.
### Расширяемость
Добавление нового канала (на схеме New Service) сводится к созданию нового микросервиса и подписке на соответствующую очередь, без изменения логики Gateway.
### Мониторинг
Все компоненты системы отправляют метрики в Prometheus с визуализацией в Grafana для отслеживания состояния системы в реальном времени.
### База данных
При отправке в базе данных обновляется состояние отправленных уведомлений: отправлено успешно, ошибка, повторная отправка. Можно проследить историю статусов уведомления со всеми состояниями и временными метками.

## 📌 Функциональность
- Прием и маршрутизация уведомлений через единый REST API шлюз
- Асинхронная отправка сообщений через очереди (RabbitMQ / Kafka)
- Поддержка каналов отправки: Email, SMS, Push-уведомления
- Гибкое добавление новых каналов без изменения основной логики
- Сохранение истории и статусов отправки в PostgreSQL / MongoDB
- Механизм автоматических повторных попыток (Retry) при сбоях
- Сбор метрик и мониторинг состояния системы (Prometheus + Grafana)

## 🛠 Технологии
- Язык программирования: C# (.NET Core).
- Архитектура: микросервисная.
- Брокер сообщений: RabbitMQ или Kafka.
- База данных: PostgreSQL или MongoDB.
- Мониторинг: Prometheus, Grafana.
- Логирование: ELK Stack (Elasticsearch, Logstash, Kibana).

## 🚀 Запуск проекта

### 1. Клонирование репозитория
```bash
git clone https://github.com/KristinaVavilina/Notification-service.git
cd Notification-service
```

### 2. Запуск приложения
```bash
docker-compose up
```

### 3. Отправка запросов
swagger доступен по адресу http://localhost/swagger/index.html 

Выберите метод POST в Swagger UI, нажмите кнопку Try it out и вставьте тело запроса в поле Request body.
Система поддерживает 4 типа каналов, которые указываются в поле "channelType": email, sms, push, telegram.

Альтернативно отправка json на http://localhost/notification/publish

Шаблоны JSON для каждого варианта:

#### 📧 Email
```json
{
  "channelType": "email",
  "recipient": "example@gmail.com",
  "subject": "Тема письма",
  "content": "Текст сообщения...",
  "metadata": {}
}
```

#### 📱 SMS
```json
{
  "channelType": "sms",
  "recipient": "+79990000000",
  "subject": "SMS",
  "content": "Ваш код...",
  "metadata": {}
}
```

#### 🔔 Push-уведомление
```json
{
  "channelType": "push",
  "recipient": "device_token_or_phone",
  "subject": "Заголовок Push",
  "content": "Текст уведомления",
  "metadata": {}
}
```

#### ✈️ Telegram
```json
{
  "channelType": "telegram",
  "recipient": "telegram_id",
  "subject": "Telegram Message",
  "content": "Текст сообщения...",
  "metadata": {}
}
```

## 📜 Логирование и метрики
- Логи отправляются в `elasticsearch` через `logstash`, их можно просмотреть в `kibana`.
- Метрики отправляются в `prometheus`, их можно просмотреть в `grafana`.

Также добавлены соответствующие метрики успешно отправленных сообщений/неудачно отправленных сообщений.
